# Техническое задание: Employee Time Tracker

Oct 28, 2026 · @nevorahq digital

Документ задаёт требования к веб-приложению учёта рабочего времени сотрудников: что система должна делать, какие правила нельзя нарушать и по каким признакам работа считается принятой.

## 1. Назначение и основания

Система позволяет небольшой команде фиксировать, кто, над какой задачей и сколько работал, и получать итоги по сотрудникам и периодам. Источник истины — файл SQLite; активный таймер обязан пережить реальный перезапуск сервера.

**Основания.** Требования собраны из трёх источников; при расхождении действует порядок от первого к последнему:

1. Это ТЗ.
2. Исходное задание «Build a Complete Employee Time Tracking Web Application» (документ проекта «test web app») — база для разделов 4, 9, 11 и 12.
3. Инструкции проекта — правила разработки и инварианты таймера (раздел 5).

От исходного задания это ТЗ отличается в двух местах, оба решения приняты 28.10.2026: стек — Next.js вместо React + Vite + Express (раздел 3), и имена сотрудников не обязаны быть уникальными (FR-EMP-5).

**Приоритеты.** MUST — обязательно для приёмки. SHOULD — делается, если этап укладывается в бюджет времени; отсутствие SHOULD не блокирует приёмку.

**Термины**

| Термин | Значение |
| --- | --- |
| Запись времени | Одна строка в `time_entries`: сотрудник, описание задачи, `startedAt`, `endedAt` |
| Активная запись (таймер) | Запись с `endedAt = null` |
| Завершённая запись | Запись с `endedAt >= startedAt` |
| Период отчёта | Полуоткрытый интервал `[from, to)` в UTC-instants |
| Вклад записи | Часть записи, попавшая в период: `max(0, min(end, to) − max(start, from))` |
| `evaluatedAt` | Момент, на который считается активная запись; фиксируется один раз на запрос |
| Provisional | Время активной записи: оценка до `evaluatedAt`, не итог |
| Рестарт | Остановка и новый запуск процесса сервера на том же файле БД |

## 2. Границы проекта

Работа начинается с пустой папки и заканчивается рабочим приложением с тестами и README. Планирование без реализации не считается результатом.

**Входит в проект**

- Управление сотрудниками: список и создание.
- Таймер по задаче: старт, стоп, одновременная работа разных сотрудников, восстановление после рестарта сервера и перезагрузки страницы.
- История записей с фильтрами по сотруднику и диапазону дат.
- Отчёты: итоги по сотрудникам и общий итог за период.
- Health-check с реальной проверкой базы.
- Автотесты, README с разделами AI Usage и Bugs Found and Fixed, финальный отчёт.

**Не входит**

- Аутентификация, роли и права доступа, мультитенантность.
- Платежи и любые бизнес-функции, не описанные в этом документе.
- Редактирование и удаление записей времени, ручная корректировка времени, автоматическая остановка «забытых» таймеров.
- Удаление и редактирование сотрудников (в исходном задании опционально; здесь не реализуется, чтобы не рисковать потерей истории).
- Экспорт данных, уведомления, интеграции с внешними системами.
- Деплой в публичный интернет. Публичная демо-ссылка без аутентификации не публикуется.

Все данные в примерах, фикстурах и скриншотах — выдуманные.

## 5. Бизнес-правила и инварианты таймера

Эти правила нельзя ослаблять без явного согласования. Каждое правило должно держаться сразу на двух уровнях: в коде сервиса и в базе данных, где SQLite это позволяет.

| ID | Инвариант | Как обеспечивается |
| --- | --- | --- |
| BR-1 | У сотрудника не более одного активного таймера | Partial unique index на `time_entries(employee_id) WHERE ended_at IS NULL` + проверка в сервисе; `SQLITE_CONSTRAINT_UNIQUE` → `409 TIMER_ALREADY_RUNNING` |
| BR-2 | Таймеры разных сотрудников могут идти одновременно | Индекс по `employee_id`, а не глобальный |
| BR-3 | Активная запись: валидный `startedAt`, `endedAt = null`. Завершённая: `endedAt >= startedAt` | `CHECK (ended_at IS NULL OR ended_at >= started_at)` и числовые метки времени в `STRICT`-таблице |
| BR-4 | Старт атомарен при конкурентных запросах | Проверка сотрудника и `INSERT` в одной транзакции `BEGIN IMMEDIATE`; индекс — последняя линия защиты между процессами и потоками |
| BR-5 | Стоп не создаёт дубликата и не перезаписывает уже завершённую запись | `UPDATE … SET ended_at = ? WHERE id = ? AND ended_at IS NULL RETURNING *` (compare-and-set); 0 строк → `404` или `409` |
| BR-6 | Завершение приложения не останавливает таймеры | Ни один обработчик сигналов и shutdown-хук не меняет `time_entries`; `synchronous = FULL` держит закоммиченное при `kill -9` |
| BR-7 | Активные таймеры восстанавливаются из хранилища с исходными `id` и `startedAt` | Состояние только в БД; автовосстановление не изменяет исторические записи |
| BR-8 | Клиентский интервал не определяет сохранённую длительность | UI считает `Date.now() − startedAt` только для отображения; сервер не принимает от клиента ни время, ни длительность |
| BR-9 | История не теряется | `ON DELETE RESTRICT`; нет эндпоинтов `DELETE`/`PUT`; миграции никогда не делают `DROP`; база не пересоздаётся при старте |
| BR-10 | Нарушения ограничений SQLite — это бизнес-конфликты, а не «500» | Маппинг `SQLITE_CONSTRAINT_*` → `409` с бизнес-кодом; блокировка БД (`SQLITE_BUSY`, `SQLITE_LOCKED`) → `503 DB_BUSY` |
| BR-11 | Время детерминированно тестируется | Всё серверное время берётся из инъектируемого `Clock` (в тестах — `FakeClock`) |
| BR-12 | Для активной записи конец никогда не выдумывается | Отчёт берёт `evaluatedAt` как верхнюю границу временно, без записи в базу |

Поведение при откате системных часов — FR-TMR-10. Работа более чем в одном процессе на одном файле БД не заявляется как поддерживаемый режим, но BR-1 и BR-4 должны выдерживать и его.

## 6. Семантика времени и отчётов

Время хранится как целое число миллисекунд Unix epoch (UTC), в API отдаётся как ISO 8601 с `Z`. Длительность всегда вычисляется из разницы меток, никогда — из отформатированных строк и не из числа тиков клиента.

**Формула вклада записи в период** (одна чистая функция, целые миллисекунды, без округления):

```latex
\text{contribution} = \max\bigl(0,\; \min(\text{end},\, \text{to}) - \max(\text{start},\, \text{from})\bigr)
```

Для активной записи `end = evaluatedAt`; в базе она не меняется.

**Правила**

- Интервал отчёта полуоткрытый `[from, to)`. Запись, закончившаяся ровно в `from`, или начавшаяся ровно в `to`, вклада не даёт.
- Часовой пояс отчёта — пояс браузера. Клиент переводит выбранные календарные даты в instants: `from` — локальная полночь даты начала, `to` — локальная полночь дня после выбранной даты окончания, то есть конечная дата включительна. На переходе на летнее и зимнее время сутки длятся 23 и 25 ч.
- Сервер не знает о часовых поясах: он принимает только ISO 8601 instants со смещением (`Z` или `+02:00`). Дата без времени и без смещения отклоняется как неоднозначная: `new Date('2026-10-01')` парсится как UTC и даёт сдвиг границ.
- Активные записи считаются до `evaluatedAt`, помечаются `isActive: true`, их время идёт в `provisionalMs`, а `endedAt` остаётся `null`. В UI — бейдж «In progress» и пометка «as of HH:MM».
- `evaluatedAt` фиксируется один раз на запрос и возвращается в ответе.
- Каждая запись даёт ровно один вклад: двойного учёта нет, время вне периода не считается.
- Округление — только в UI, в едином формате длительности (например, `H:MM:SS`). Суммы никогда не считаются из округлённых значений.
- Выборка кандидатов в SQL делается предикатом `started_at < :to AND COALESCE(ended_at, :evaluatedAt) > :from`; агрегация — в сервисе через ту же функцию вклада, чтобы у правила была одна реализация.

**Примеры границ** (период `[10:00, 12:00)` UTC, 28.10.2026)

| Запись | Вклад | Почему |
| --- | --- | --- |
| 09:00–11:00 | 1 ч | Пересекает начало периода, считается только часть внутри |
| 11:00–13:00 | 1 ч | Пересекает конец периода |
| 08:00–10:00 | 0 | Закончилась ровно в `from` |
| 12:00–13:00 | 0 | Началась ровно в `to` |
| 06:00–07:00 | 0 | Целиком вне периода |
| активная с 11:00, `evaluatedAt` = 11:30 | 30 мин, provisional | Конец выдуман не был, верхняя граница — `evaluatedAt` |

**Форма ответа отчёта.** `period { from, to }`, `evaluatedAt`, `totals { finalizedMs, provisionalMs, totalMs }`, `employees[ { employeeId, name, finalizedMs, provisionalMs, totalMs, entryCount } ]`, `entries[ { id, employeeId, description, startedAt, endedAt, isActive, contributionMs } ]`.

## 8. Модель данных и хранение

SQLite — единственный источник истины для бизнес-данных. Две таблицы; время — `INTEGER` в миллисекундах Unix epoch UTC, id — UUID v4 (`crypto.randomUUID()`). Требуемая схема:

```sql
-- migrations/001_init.sql (применяется в транзакции, версия в PRAGMA user_version)
CREATE TABLE employees (
  id          TEXT    PRIMARY KEY,
  name        TEXT    NOT NULL
              CHECK (length(name) BETWEEN 1 AND 100 AND name = trim(name)),
  created_at  INTEGER NOT NULL
) STRICT;

CREATE TABLE time_entries (
  id           TEXT    PRIMARY KEY,
  employee_id  TEXT    NOT NULL REFERENCES employees(id) ON DELETE RESTRICT,
  description  TEXT    NOT NULL
               CHECK (length(description) BETWEEN 1 AND 500 AND description = trim(description)),
  started_at   INTEGER NOT NULL,
  ended_at     INTEGER,
  created_at   INTEGER NOT NULL,
  CHECK (ended_at IS NULL OR ended_at >= started_at)
) STRICT;

-- инвариант «один активный таймер на сотрудника» на уровне БД
CREATE UNIQUE INDEX ux_time_entries_one_active
  ON time_entries(employee_id) WHERE ended_at IS NULL;
-- история и отчёты по сотруднику и по всем
CREATE INDEX ix_time_entries_employee_started ON time_entries(employee_id, started_at);
CREATE INDEX ix_time_entries_started ON time_entries(started_at);
```

| ID | Требование | Приоритет |
| --- | --- | --- |
| DB-1 | Путь к файлу БД задаётся `DATABASE_PATH`; значение по умолчанию документируется в `.env.example`; файл находится вне `.next` и в `.gitignore` | MUST |
| DB-2 | На каждом соединении: `foreign_keys = ON`, `journal_mode = WAL`, `busy_timeout = 5000`, `synchronous = FULL` | MUST |
| DB-3 | Схема создаётся миграциями по `PRAGMA user_version`: применяются только неприменённые, каждая в транзакции; повторный запуск не трогает данные | MUST |
| DB-4 | Мигратор создаёт каталог БД, никогда не делает `DROP` и не пересоздаёт существующую базу | MUST |
| DB-5 | Только параметризованные запросы (prepared statements); конкатенация ввода в SQL запрещена | MUST |
| DB-6 | Состояние бизнеса не дублируется в памяти процесса; исключение — соединение с БД | MUST |
| DB-7 | Состояние базы для автотестов — временный файл на каждый тест; `:memory:` и рабочая БД не используются | MUST |

## 9. REST API

API реализуется Route Handlers в `app/api/**/route.ts`. У всех ответов один конверт: успех — `{ "data": … }`, ошибка — `{ "error": { "code", "message", "details"? } }`. Время в ответах — ISO 8601 UTC. Все входные данные валидируются на сервере.

```ts
type Employee  = { id: string; name: string; createdAt: string };
type TimeEntry = {
  id: string; employeeId: string; employeeName: string;
  description: string; startedAt: string; endedAt: string | null;
};
```

| Эндпоинт | Вход | Успех | Ошибки |
| --- | --- | --- | --- |
| `GET /api/health` | — | `200 { status: "ok", database: "ok" }` | `503 DATABASE_UNAVAILABLE`, если `SELECT 1` падает |
| `GET /api/employees` | — | `200 Employee[]`, сортировка по имени | — |
| `POST /api/employees` | `{ name }` | `201 Employee` | `400 VALIDATION_ERROR` |
| `GET /api/timer/active` | `?employeeId` | `200 { timers: TimeEntry[], serverTime }` | `400 VALIDATION_ERROR` |
| `POST /api/timer/start` | `{ employeeId, description }` | `201 TimeEntry` | `400 VALIDATION_ERROR`, `404 EMPLOYEE_NOT_FOUND`, `409 TIMER_ALREADY_RUNNING` |
| `POST /api/timer/:id/stop` | — | `200 TimeEntry` | `400` (id не UUID), `404 TIMER_NOT_FOUND`, `409 TIMER_ALREADY_STOPPED` |
| `GET /api/time-entries` | `?employeeId&from&to&limit&offset` | `200 { entries: TimeEntry[], total }`, новые сверху | `400 VALIDATION_ERROR`, `400 INVALID_DATE_RANGE` |
| `GET /api/reports/summary` | `?from&to` (обяз.), `?employeeId` | `200 Report` (форма — в разделе 6) | `400 VALIDATION_ERROR`, `400 INVALID_DATE_RANGE` |

Пример запроса старта и ошибки:

```json
POST /api/timer/start
{ "employeeId": "<uuid>", "description": "Implement reporting API" }

409
{ "error": { "code": "TIMER_ALREADY_RUNNING", "message": "This employee already has an active timer." } }
```

**Коды ошибок** (стабильны, машинно-читаемы, без stack trace, SQL и внутренних путей)

| Код | HTTP | Когда | Приоритет |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Невалидное тело, query или id; дата без смещения (в `message` — пример формата) | MUST |
| `INVALID_JSON` | 400 | Тело запроса — невалидный JSON | MUST |
| `INVALID_DATE_RANGE` | 400 | `from >= to` | MUST |
| `EMPLOYEE_NOT_FOUND` | 404 | Сотрудника с таким id нет | MUST |
| `TIMER_NOT_FOUND` | 404 | Записи с таким id нет | MUST |
| `NOT_FOUND` | 404 | Неизвестный `/api/*` (JSON, не HTML) | MUST |
| `TIMER_ALREADY_RUNNING` | 409 | У сотрудника уже есть активный таймер | MUST |
| `TIMER_ALREADY_STOPPED` | 409 | Таймер уже остановлен | MUST |
| `DATABASE_UNAVAILABLE` | 503 | Нет соединения с БД (health) | MUST |
| `DB_BUSY` | 503 | Блокировка БД не снялась за `busy_timeout`; заголовок `Retry-After: 1` | MUST |
| `INTERNAL_ERROR` | 500 | Непредвиденная ошибка; полная ошибка — только в лог сервера | MUST |
| `PAYLOAD_TOO_LARGE` | 413 | Тело больше 10 KB | SHOULD |

**Дополнительные правила**

- Даты `from` и `to` — ISO 8601 instant со смещением (`Z` или `+02:00`); дата без времени отклоняется.
- `serverTime` в `/api/timer/active` — время сервера в момент ответа; на нём строится тест восстановления и (SHOULD) поправка часов клиента.
- `limit` — по умолчанию 100, `offset` — 0. SHOULD: потолок `limit` 500 и ограничение диапазона `from`–`to` 366 днями.
- Валидация строк: `trim()`, затем длина 1–100 для имени и 1–500 для описания — те же границы, что и в `CHECK`.
- Все route-файлы объявляют `runtime = 'nodejs'` и `dynamic = 'force-dynamic'`; ответы с активными таймерами не кэшируются.
- `GET /api/health` не возвращает «ok», когда БД недоступна.
- Контракт API — общий интерфейс: при его изменении одним коммитом обновляются клиент, тесты и README.

## 11. Тестирование: 32 обязательных сценария

Тесты — основной результат, а не добавка после. Каждый тест работает на своём временном файле БД и с `FakeClock`; `:memory:` и рабочая БД не используются. Имя теста начинается с ID сценария (`[S7]`, диапазон — `[S13-S21]`), а `scripts/check-scenarios.mjs` падает, если хотя бы один ID отсутствует. API тестируется вызовом handler-функций с реальным Web `Request`.

### 11.1 Сотрудники

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| S1 | Успешное создание сотрудника | `201`, есть `id` и `createdAt`, имя очищено от пробелов по краям |
| S2 | Пустое или состоящее из пробелов имя | `400 VALIDATION_ERROR`, строка в БД не появляется |
| S3 | Список сотрудников | Все созданные, сортировка по имени |
| S4 | Старт для несуществующего сотрудника | `404 EMPLOYEE_NOT_FOUND`; невалидный id → `400` |

### 11.2 Таймер

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| S5 | Успешный старт | `201`, `endedAt = null`, `startedAt` = время сервера |
| S6 | Успешный стоп | `200`, та же запись, `endedAt >= startedAt` |
| S7 | Второй старт того же сотрудника | `409 TIMER_ALREADY_RUNNING`, в БД одна активная строка |

Это настоящий интеграционный тест на файле БД, а не сброс React-состояния или очистка объекта в памяти. Шаги S13–S21 идут подряд в одном тесте.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| S22 | Агрегация по сотруднику за период | Сумма вкладов записей в миллисекундах |

### 11.5 Дополнительные обязательные проверки

| Проверка | Уровень | Что должно происходить |
| --- | --- | --- |
| Жёсткий рестарт процесса | smoke над `next start` | Сотрудник + старт → `kill -9` → новый `next start` → те же `id` и `startedAt` → стоп → одна строка |
| Параллельный стоп | worker\_threads | Ровно один `200`, остальные `409 TIMER_ALREADY_STOPPED` |
| Разные сотрудники под нагрузкой | worker\_threads | Все старты успешны, индекс не глобальный |
| Мутационная проверка | ручная, один раз | Временно убрать partial unique index — S7 и S12 должны упасть |
| Ограничения БД | DB | Вторая активная строка падает на индексе; `CHECK`, FK; миграции идемпотентны |
| Health | handler | `200` на живой БД, `503` после `db.close()` |
| Откат часов | handler + FakeClock | `now < startedAt` → `endedAt = startedAt` |
| Даты и DST | unit, `TZ=Europe/Chisinau` | Сутки 2026-03-29 — 23 ч, 2026-10-25 — 25 ч; дата без смещения → `400` |
| Импорт серверного кода | ESLint | `@/server/*` нельзя импортировать из клиентского кода |
| Frontend | React Testing Library | Валидация форм, `disabled` во время запроса, восстановление таймера, пустой отчёт, конвертация локальных дат |

**Правила.** Конкурентные тесты не пишутся через `Promise.all` в одном процессе: better-sqlite3 синхронный, и такой тест проходит даже без индекса. Часовой пояс тестов зафиксирован (`TZ=Europe/Chisinau`). Найденный баг сначала воспроизводится падающим тестом, потом чинится. Тесты не ослабляются и не удаляются ради зелёной сборки; если тест неверен, объяснить, почему, и исправить сам тест.

Краткие архитектурные решения (ADR-заметки в `docs/decisions.md` или в README): выбор Next.js, better-sqlite3 без ORM, неуникальные имена, `epoch-ms` вместо ISO-строк в БД, обработка отката часов, политика `503 DB_BUSY`. Каждая запись — контекст, решение, последствия, дата.

## 14. Допущения и открытые вопросы

### 14.1 Принятые решения

| № | Решение | Основание |
| --- | --- | --- |
| 1 | Имена сотрудников **не уникальны**; при совпадении UI показывает суффикс `id` (решение от 28.10.2026) | Исходное ТЗ разрешает дубликаты при условии документирования |
| 2 | Удаление сотрудников не реализуется | Опционально в исходном ТЗ; исключает риск потери истории |
| 3 | Время в БД — целые миллисекунды UTC | Точная арифметика, без разбора строк |
| 4 | Часовой пояс отчёта задаёт браузер; сервер не зависит от своей TZ | Исключает дрейф при переносе сервера |
| 5 | Дата без смещения в фильтре отклоняется с понятным `400` | Исключает двусмысленность |
| 6 | Активный таймер в отчёте — только `provisionalMs` | Нельзя выдумывать `endedAt` |
| 7 | При откате системных часов `endedAt = max(now, startedAt)` с предупреждением в логе | Сохраняет инвариант `endedAt >= startedAt` |
| 8 | Среда исполнения — один инстанс Node ≥ 22 | Масштаб: десятки сотрудников, десятки тысяч записей |

### 14.2 Открытые вопросы

| № | Вопрос | Риск, если не выяснить |
| --- | --- | --- |
| 1 | Согласована ли смена стека (React + Vite + Express → Next.js) с заказчиком или проверяющим? | Если это тестовое задание, замена может не засчитаться |
| 2 | Соберётся ли `better-sqlite3` на Node 22 / arm64 в целевой среде? | Fallback — `node:sqlite`; проверяется в spike |
| 3 | Корректно ли отрабатывают тест на `worker_threads` и `kill -9` в целевой среде? | Не проверено до spike |
| 4 | Нужна ли выгрузка отчёта (CSV) и удаление сотрудников? | Вне скоупа, пока явно не запрошено |

> Оценки трудоёмкости этапов в плане — мои, не из исходного ТЗ. Это не обязательное требование; их можно менять.
