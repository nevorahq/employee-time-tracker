# Employee Time Tracker

Веб-приложение учёта рабочего времени сотрудников: кто, над какой задачей и сколько работал. Источник истины — файл SQLite; активный таймер переживает реальный перезапуск сервера (в том числе `kill -9`).

> **Только для локального использования.** В приложении нет аутентификации, ролей и прав доступа. Оно слушает `127.0.0.1` и **не предназначено для открытого доступа из интернета**. Публичный деплой не поддерживается.

## 1. Назначение проекта

Небольшая команда (десятки сотрудников, десятки тысяч записей, один инстанс процесса) фиксирует время по задачам и получает итоги по сотрудникам и периодам. Требования описаны в [Техническом задании](Техническое%20задание%20Employee%20Time%20Tracker.md), план работ — в [плане разработки](План%20разработки%20Employee%20Time%20Tracker.md).

## 2. Список возможностей

- **Сотрудники:** список (по имени) и создание. Имя обрезается по краям, 1–100 символов, без управляющих символов. Одинаковые имена допускаются.
- **Таймер:** старт по задаче (описание 1–500 символов), стоп, не более одного активного таймера на сотрудника, таймеры разных сотрудников идут параллельно.
- **Восстановление:** активные таймеры читаются из БД при каждой загрузке страницы; рестарт сервера их не трогает.
- **История (Timesheet):** записи с фильтром по сотруднику и диапазону дат, новые сверху, постраничный вывод (25 на страницу) и общий `total`; идущая запись помечена «In progress». Вид «список» или «сетка», группировка по дате, сотруднику или без неё.
- **Экспорт в CSV:** кнопка **Export** выгружает все записи, подходящие под текущие фильтры (не только страницу на экране). Ячейки, начинающиеся с `=`, `+`, `-`, `@`, экранируются апострофом (защита от CSV-инъекций). Экспорт выполняет браузер по публичному API, отдельного серверного эндпоинта нет.
- **Отчёты:** итог по каждому сотруднику и общий итог за период `[from, to)`; идущие таймеры включаются как provisional (до момента расчёта).
- **Health-check** с реальным запросом к БД: `GET /api/health`.
- **Демо-данные:** `npm run seed` (5 вымышленных сотрудников, две недели записей, один идущий таймер).

## 3. Стек и обоснование выбора

| Слой | Выбор |
| --- | --- |
| Фреймворк | Next.js 16 (App Router), React 19, TypeScript (`strict`, `noUncheckedIndexedAccess`) |
| API | Route Handlers (`runtime = 'nodejs'`, `dynamic = 'force-dynamic'`) |
| БД | SQLite через `better-sqlite3`, без ORM |
| Валидация | Zod 4, схемы общие для сервера и клиента (`src/shared/`) |
| Стили | Обычный CSS |
| Тесты | Vitest 5, React Testing Library, jsdom, `worker_threads`, smoke-скрипт над `next start` |
| Качество | ESLint (flat config + `eslint-config-next`), `tsc --noEmit` |

**Почему Next.js, а не React + Vite + Express (рекомендация исходного задания).** ТЗ допускает другой стек при обосновании. Next.js даёт UI и API в одном процессе и одном origin: не нужны proxy и CORS, один `build`, один процесс для перезапуска. Цена: фреймворк тяжелее связки Vite + Express; жизненным циклом сервера управляет `next start`; у Route Handlers нет цепочки middleware, поэтому валидацию и обработку ошибок выполняют `parseJson`, `parseQuery` и `withErrors`. Подробнее — в [docs/decisions.md](docs/decisions.md). Если задание проверяется по исходной рекомендации стека, смена стека может не засчитаться: это открытый вопрос ТЗ (14.2, №1).

Версии зависимостей зафиксированы точно (`save-exact=true`), `package-lock.json` в репозитории.

## 4. Архитектура и структура каталогов

Запрос идёт по слоям: **route → handlers → services → repositories → SQLite**. Бизнес-правила не зависят от Next.js и тестируются без запуска сервера; последняя гарантия инвариантов — индексы и `CHECK` в SQLite. Браузер только отображает состояние сервера.

```text
app/
  layout.tsx, page.tsx, globals.css   # серверная оболочка без данных
  api/**/route.ts                     # тонкие route-файлы (+ [...slug] — JSON 404)
src/
  shared/    # контракт API: Zod-схемы, типы, коды ошибок (используется и клиентом)
  server/    # только серверный код; клиент его импортировать не может (ESLint)
    db/            # openDatabase, прагмы, миграции по PRAGMA user_version
    domain/        # time.ts (overlapMs), errors.ts (AppError), range.ts, dto.ts
    repositories/  # весь SQL, только prepared statements
    services/      # employees, timer, history, reports — бизнес-правила
    handlers/      # Request → Response; http.ts: parseJson, parseQuery, withErrors
    container.ts   # createContainer + ленивый getContainer (на globalThis)
    routes.ts      # route(): 503 JSON, если БД не открывается
    seed.ts        # демо-данные
  client/    # 'use client': TimeTrackerApp, features/{employees,timer,history,reports}, lib/
tests/       # unit, integration, client, e2e/smoke.mjs, workers, helpers
scripts/     # check-scenarios.mjs, seed.ts
docs/decisions.md
```

Соединение с БД открывается лениво, один раз на процесс, и хранится на `globalThis`, чтобы hot reload в `next dev` не открывал новое соединение на каждое сохранение. При импорте модулей БД не открывается и при `next build` не создаётся.

## 8. Инициализация БД и поведение персистентности

- Файл БД и схема создаются при **первом обращении к API**, а не при импорте или сборке. Миграции применяются по `PRAGMA user_version`: только ещё не применённые, каждая в транзакции; повторный запуск данные не трогает. Мигратор никогда не делает `DROP` и не пересоздаёт существующую базу.
- На каждом соединении: `foreign_keys = ON`, `journal_mode = WAL`, `busy_timeout = 5000`, `synchronous = FULL` (закоммиченное переживает `kill -9`). Рядом с файлом появляются `-wal` и `-shm` — это нормально.
- Время хранится целыми миллисекундами Unix epoch (UTC).
- В приложении нет `DELETE`/`PUT`-эндпоинтов, а миграции только добавляют схему. Чтобы начать с чистой БД, остановите сервер и удалите файл БД вручную. Для резервной копии остановите сервер и скопируйте файл вместе с `-wal` и `-shm`.
- Если файл БД открыть нельзя (неверный `DATABASE_PATH`, нет прав), API отвечает `503 DATABASE_UNAVAILABLE` и повторяет попытку при следующем запросе.

| Эндпоинт | Вход | Успех | Ошибки |
| --- | --- | --- | --- |
| `GET /api/health` | — | `200 { status: "ok", database: "ok" }` | `503 DATABASE_UNAVAILABLE` |
| `GET /api/employees` | — | `200 Employee[]` | — |
| `POST /api/employees` | `{ name }` | `201 Employee` | `400 VALIDATION_ERROR` |
| `GET /api/timer/active` | `?employeeId` | `200 { timers, serverTime }` | `400` |
| `POST /api/timer/start` | `{ employeeId, description }` | `201 TimeEntry` | `400`, `404 EMPLOYEE_NOT_FOUND`, `409 TIMER_ALREADY_RUNNING` |
| `POST /api/timer/:id/stop` | — | `200 TimeEntry` | `400`, `404 TIMER_NOT_FOUND`, `409 TIMER_ALREADY_STOPPED` |
| `GET /api/time-entries` | `?employeeId&from&to&limit&offset` | `200 { entries, total }` | `400 VALIDATION_ERROR`, `400 INVALID_DATE_RANGE` |
| `GET /api/reports/summary` | `?from&to` (обяз.), `?employeeId` | `200 Report` | `400 VALIDATION_ERROR`, `400 INVALID_DATE_RANGE` |

Остальные коды: `INVALID_JSON` (400), `NOT_FOUND` (404, неизвестный `/api/*`, всегда JSON), `PAYLOAD_TOO_LARGE` (413, тело > 10 KB), `DB_BUSY` (503 с `Retry-After: 1`), `INTERNAL_ERROR` (500, без stack trace, SQL и путей; подробности только в логе сервера). `limit` по умолчанию 100, максимум 500; диапазон `from`–`to` не длиннее 366 суток (с запасом на один час перехода времени). UUID принимаются в любом регистре. Все ответы отдаются с `Cache-Control: no-store`.

## 13. Примеры сценариев сотрудник + таймер

1. Откройте `http://127.0.0.1:3000`. В боковой навигации четыре раздела: **Timesheet**, **Active Timer**, **Reports**, **Employees**. В **Employees** добавьте «Ada Example» и «Bob Sample».
2. В **Active Timer** выберите Ada, введите «Write report», нажмите **Start**: появится карточка с тикающим временем.
3. Выберите Bob и запустите второй таймер: оба идут одновременно.
4. Снова выберите Ada: Start блокируется, показывается предупреждение «already has an active timer».
5. Нажмите **Stop** у Ada: запись появилась в **Timesheet** с длительностью. Сотрудник и диапазон дат фильтруют историю, **Group By** меняет группировку, **Export** сохраняет CSV.
6. В **Reports** выберите даты и сотрудника (или All) и нажмите **Run report**: итог по каждому и общий; идущий таймер Bob помечен «In progress · as of HH:MM» и считается provisional.

Если у двух сотрудников одинаковое имя, они показываются как `Alice Smith · #a1b2` и `Alice Smith · #c3d4` (решение зафиксировано в [docs/decisions.md](docs/decisions.md), ADR-3).

## 14. Восстановление таймера после перезапуска

Состояние таймера хранится только в БД: строка с `ended_at IS NULL`. Никакой shutdown-хук не обращается к `time_entries` (это проверяет тест), а `GET /api/timer/active` читает таймеры из БД при каждой загрузке страницы. Время работы в UI считается как `Date.now() + поправка − startedAt` раз в секунду и нигде не сохраняется; поправка берётся из `serverTime`, поэтому расхождение часов браузера и сервера не искажает значение. Простой сервера входит в прошедшее время.

Проверить вручную:

```bash
npm run build && npm start             # запустите таймер в браузере
kill -9 <pid процесса next-server>     # жёсткая остановка
npm start                              # обновите страницу
```

Страница покажет тот же таймер с тем же `startedAt` и временем, включающим простой. Автоматически это проверяют `tests/integration/restart.test.ts` (S13–S21, на файле БД) и `tests/e2e/smoke.mjs` (настоящий `next start` и `SIGKILL`). Закрытие соединения без `close()` (имитация `kill -9` в тесте) данные не теряет.

## 15. Семантика интервала отчёта и длительностей

- Интервал отчёта полуоткрытый **`[from, to)`**. Запись, закончившаяся ровно в `from` или начавшаяся ровно в `to`, вклада не даёт. Вклад записи: `max(0, min(end, to) − max(start, from))` в целых миллисекундах; формула в одном месте — `overlapMs` в `src/server/domain/time.ts`. Историю и отчёт отбирает один и тот же предикат: `started_at < :to AND COALESCE(ended_at, :evaluatedAt) > :from`.
- **Provisional.** Для идущей записи `end = evaluatedAt` (момент расчёта, фиксируется один раз на запрос и возвращается в ответе). `endedAt` не выдумывается и в БД не пишется; время идёт в `provisionalMs`, запись помечена `isActive: true`.
- **Инварианты сумм:** `totalMs` = Σ по сотрудникам = Σ по записям; `totalMs = finalizedMs + provisionalMs`.
- **Часовой пояс.** Отчёт и фильтры используют пояс **браузера** (его имя показано рядом с фильтром). Браузер переводит календарные даты в instants: `from` — локальная полночь даты начала, `to` — локальная полночь следующего за датой окончания дня, то есть конечная дата **включительна**. Сервер часовых поясов не знает: принимает только ISO 8601 со смещением, а дату без смещения отклоняет с `400`, потому что `new Date('2026-10-01')` разбирается как UTC и сдвинул бы границы.
- **DST.** На переходах сутки длятся 23 и 25 часов (в `Europe/Chisinau`: 2026-03-29 — 23 ч, 2026-10-25 — 25 ч); это покрыто тестами.
- **Округление** — только в UI (`H:MM:SS`, секунды отбрасываются); суммы никогда не считаются из округлённых значений.
- **Откат часов сервера:** если `now < startedAt`, то `endedAt = startedAt`, в лог пишется предупреждение (ADR-5).
- Пустой отчёт — штатный результат с нулями и пустыми массивами, не ошибка.

## 17. Bugs Found and Fixed

В этот раздел входят только дефекты, найденные при реализации и воспроизведённые падающим тестом **до** исправления.

### Баг 1. Недоступная БД ломала контракт API и health-check

- **Симптом.** При неверном `DATABASE_PATH` (например, `/dev/null/x.db`) `GET /api/health` не отвечал `503 DATABASE_UNAVAILABLE`, а завершался необработанным исключением (`ENOTDIR`); остальные эндпоинты вели себя так же.
- **Первопричина.** Route-файлы вызывали `getContainer()` вне `withErrors`, и ошибка открытия БД не превращалась в JSON-ответ.
- **Исправление.** Route-файлы создаются через `route()` (`src/server/routes.ts`): неудачное открытие отвечает `503 DATABASE_UNAVAILABLE` без деталей, подробности пишутся только в лог, неудача не кэшируется, и следующий запрос пробует открыть БД снова.
- **Проверка.** `tests/integration/route-wiring.test.ts` (3 теста, до исправления красные) и вручную на реальном `next start` с неверным путём: `503` и JSON без путей и стека. Коммит `f1aaf30`.

### Баг 2. UUID в верхнем регистре не находили существующие записи

- **Симптом.** Таймер или сотрудник с корректным id, записанным заглавными буквами, давал `404 TIMER_NOT_FOUND` / `EMPLOYEE_NOT_FOUND`.
- **Первопричина.** `z.uuid()` принимает любой регистр, а поиск в SQLite по `TEXT`-ключу чувствителен к регистру; id хранятся в нижнем.
- **Исправление.** `idSchema` приводит id к нижнему регистру.
- **Проверка.** `tests/integration/timer.test.ts`: «UUIDs case-insensitively» (до исправления красный). Коммит `f1aaf30`.

### Баг 3. Управляющие символы в имени и описании

- **Симптом.** Имя или описание из одного `\u0000` (или начинающееся с него) давало `500 INTERNAL_ERROR` вместо `400`; NUL внутри строки молча сохранялся в БД.
- **Первопричина.** `length()` в SQLite считает символы только до первого NUL, поэтому `CHECK (length(...) BETWEEN 1 AND …)` расходился со схемой Zod, которая NUL пропускала.
- **Исправление.** Общие схемы отклоняют управляющие символы C0 и DEL (в описании допустимы перевод строки и табуляция), поэтому API отвечает `400 VALIDATION_ERROR`, а клиент применяет то же правило.
- **Проверка.** 10 тестов в `employees.test.ts` и `timer.test.ts` (до исправления красные) и один на допустимые переводы строк в описании. Коммит `77e074b`.

### Исследовано, но не подтверждено как дефект

- Форматирование полуночи как `24:00` в `Intl.DateTimeFormat('en-GB', { hour12: false })` — не воспроизводится (`00:00`).
- `history`: `total` и `entries` читаются двумя запросами без общего снимка. Теоретически параллельная запись между ними может дать расхождение на одну запись; не воспроизведено, исправление не вносилось (см. ограничения).

### Мутационная проверка (ручная, один раз)

- **Убран только partial unique index:** упали 2 теста уровня БД (вставка второй активной строки); **S7 и S12 остались зелёными**, потому что проверка в сервисе внутри `BEGIN IMMEDIATE` сама держит инвариант (ADR-7). Это отличается от ожидания ТЗ 11.5 («S7 и S12 должны упасть») и зафиксировано как расхождение: при двух независимых слоях защиты удаление одного из них не должно ломать поведение.
- **Убраны и индекс, и проверка в сервисе:** упали S7, S12, нагрузочный тест «stop и start одного сотрудника» и оба теста уровня БД, то есть тесты чувствительны к потере защиты.
- Изменения откатывались через git, рабочее дерево после проверки чистое.

## 18. Известные ограничения и возможные улучшения

- Нет аутентификации и прав; только `127.0.0.1`; публичный деплой не поддерживается. Приложение рассчитано на один инстанс процесса.
- Нельзя редактировать и удалять записи времени и сотрудников, вручную корректировать время, автоматически останавливать «забытые» таймеры (UI предупреждает о таймерах старше 12 часов).
- CSV-экспорт есть только для истории (Timesheet); отчёты не экспортируются. Нет уведомлений, локализации и тёмной темы.
- Сортировка имён без учёта регистра работает для ASCII (`COLLATE NOCASE`); для остальных символов сравнение побайтовое.
- `GET /api/time-entries` читает `entries` и `total` двумя запросами без общего снимка (см. выше).
- `+` в смещении (`+02:00`) в строке запроса нужно кодировать как `%2B`, иначе он превращается в пробел и запрос отклоняется с понятным `400`.
- Часовой пояс отчётов задаёт браузер; если у двух пользователей разные пояса, одинаковые «даты» дают разные периоды.
- Не проверялось: Windows, Node вне 22.x, `npm run dev` с реальным hot reload при частых правках (проверен только запуск и ответы API). Проверено на macOS arm64 (локально) и Ubuntu x64 (GitHub Actions, `ubuntu-latest`).
- Возможные улучшения: общий снимок для истории (`BEGIN` на чтение), экспорт отчётов в CSV, редактирование записей с журналом изменений, выбор часового пояса отчёта.
